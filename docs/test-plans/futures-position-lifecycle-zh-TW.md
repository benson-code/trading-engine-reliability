# 測試計畫：合約倉位生命週期（開倉 → 持倉 → 強平）

> 版本 0.1 · 2026-08-05 · 作者 benson-code
> 範圍：U 本位永續合約（USDT-margined perpetual）單一交易對的倉位生命週期

---

## 0. 這份文件是什麼，不是什麼

**是什麼**：一份針對合約倉位生命週期的測試設計文件。它從風險出發，推導出要驗證哪些不變式、
在哪一層驗、用什麼邊界值驗，以及系統必須提供什麼能力才驗得起來。

**不是什麼**：

- **不是**針對任何特定交易所內部實作寫的。我沒有內部規格，本文的公式與參數
  來自永續合約的**公開通用慣例**，全部列在 §2 並標記為**待與規格確認**。
- **不是**已執行的測試報告。這裡沒有任何「通過／失敗」的宣稱。
- 標記 `【假設】` 的段落，是我基於通用慣例做的推定；規格到手後**必須逐條核對**，
  核對結果會改變 §6 的邊界值。把假設寫出來而不是藏起來，是為了讓它們可以被推翻。

**設計原則**：這份計畫刻意把重量放在**不變式（§4）**而不是案例清單（§6）。
案例會隨功能異動而過期，不變式不會——只要業務規則沒變，「帳戶淨值不得憑空產生」
就永遠該成立。案例是不變式的抽樣，不是反過來。

## 1. 範圍

### 1.1 涵蓋

| 階段 | 涵蓋內容 |
|---|---|
| **開倉** | 下單校驗、保證金凍結、槓桿與風險限額分層、部分成交、reduce-only |
| **持倉** | 未實現盈虧計算、標記價格、資金費率結算、調整槓桿／保證金 |
| **強平** | 觸發條件、部分減倉、完全強平、穿倉、保險基金、ADL |

### 1.2 明確不涵蓋

- 撮合引擎本身的價格時間優先正確性（另立計畫）
- 行情推送（WebSocket）的延遲與序號連續性（另立計畫）
- 前端 UI 呈現（本計畫止於 API 與狀態層）
- 跨交易對的組合保證金（portfolio margin）

排除項在此列出，是為了讓「沒測到」是一個**決定**，而不是一個疏漏。

## 2. 受測系統與假設

### 2.1 名詞與公式 【假設】

| 名詞 | 定義 | 備註 |
|---|---|---|
| 名目價值 Notional | `數量 × 價格` | |
| 起始保證金 IM | `名目價值 ÷ 槓桿` | 開倉時凍結 |
| 維持保證金率 MMR | 依名目價值分層 | 風險限額階梯 |
| 維持保證金 MM | `名目價值 × MMR − 速算額` | 速算額使分層邊界連續 |
| 未實現盈虧 uPnL | 多：`(標記價 − 開倉均價) × 數量`<br>空：`(開倉均價 − 標記價) × 數量` | **以標記價計算** |
| 保證金餘額 | `錢包餘額 + uPnL` | |
| 保證金率 | `MM ÷ 保證金餘額` | |
| **強平觸發條件** | **`保證金餘額 ≤ MM`** | 本計畫的核心不變式來源 |

### 2.2 標記價格 vs 最新成交價 【假設】

- **標記價格（Mark Price）**：由指數價格（多家現貨來源）加上基差移動平均導出，
  設計目的是**抵抗單一市場的瞬間操縱**。用於：未實現盈虧、強平判定。
- **最新成交價（Last Price）**：實際成交價。用於：已實現盈虧、（可選的）觸發單觸發。

> **這個區分是本計畫風險排序第一名的來源。** 若強平誤用最新成交價，
> 一根被操縱的針就能造成大規模不當強平——這是有前例的事故類型，
> 而且純功能測試看不出來，因為兩種價格在平靜市況下幾乎相同。

### 2.3 系統邊界

```
        下單 API ──► 風控前置校驗 ──► 撮合引擎
                         │                │
                         ▼                ▼
                    保證金帳本 ◄──── 成交回報
                         │
        標記價格來源 ──► 風險引擎 ──► 強平引擎 ──► 保險基金 ──► ADL
                                        │
                    資金費率排程 ────────┘
```

受測範圍是**風控前置校驗 → 保證金帳本 → 風險引擎 → 強平引擎**這條鏈，
以及它與資金費率排程的互動。撮合引擎視為可信賴的外部相依（以樁模擬成交回報）。

## 3. 風險矩陣

風險分數 = 影響 × 可能性。**測試投入依此排序**，不是依功能清單順序。

| # | 風險 | 影響 | 可能性 | 分數 | 為什麼 |
|---|---|---|---|---|---|
| **R1** | 強平誤用最新成交價而非標記價 | 極高 | 中 | **9** | 單筆異常成交造成大規模不當強平；平靜市況下測不出來 |
| **R2** | 強平重複執行（非冪等） | 極高 | 中 | **9** | 重試或雙觸發導致重複平倉／重複收費；**與支付重複扣款同構** |
| **R3** | 強平邊界的比較子錯誤（`≤` vs `<`） | 高 | 高 | **9** | 差一個最小單位決定使用者爆不爆倉；經典 off-by-one |
| **R4** | 逐倉模式的損失外溢到其他倉位／錢包 | 極高 | 低 | **6** | 破壞逐倉的核心承諾 |
| **R5** | 部分成交後保證金未正確重算 | 高 | 中 | **6** | 凍結過多→影響下單；凍結過少→風險敞口 |
| **R6** | 資金費率重複收取或漏收 | 高 | 中 | **6** | 帳目不平；**同樣是冪等問題** |
| **R7** | 風險限額分層在名目價值變動時未重新套用 | 高 | 中 | **6** | 加倉跨層後 MMR 仍用舊層 → 強平價算錯 |
| **R8** | 穿倉時使用者餘額變負且未被保險基金吸收 | 極高 | 低 | **6** | 平台承擔未預期損失 |
| **R9** | reduce-only 訂單反而增加倉位 | 高 | 低 | **4** | 語意違反；在併發下最容易發生 |
| **R10** | 調整槓桿與成交回報競態 | 中 | 中 | **4** | 保證金短暫不一致 |
| **R11** | 大規模連鎖強平時引擎延遲或積壓 | 高 | 低 | **4** | 極端行情才會出現，但出現就是系統性事件 |
| **R12** | 倉位／訂單帳本無界成長 | 中 | 中 | **4** | 長時間運行後記憶體耗盡（見 §8） |

> **R2、R6 與本專案既有資產直接對接。** `payment-api` 已經用
> `UNIQUE(idempotency_key)` + 單一交易 + 16 執行緒競賽測試證明過
> 「重試不得重複扣款」。強平與資金費率是同一個問題換一層皮：
> **一個外部觸發可能重送，而它會動到錢。** 測試手法可以直接沿用。

## 4. 系統不變式

**這一節是本計畫的核心。** 不變式是「無論輸入為何、無論時序如何，都必須成立」的性質。
它們是斷言的來源，也是 property-based 測試與混沌測試的判準。

| ID | 不變式 | 對應風險 |
|---|---|---|
| **I1** | **價值守恆**：所有帳戶淨值 + 保險基金 + 已收手續費 = 總入金 − 總出金。系統不得憑空產生或消滅價值 | R8 |
| **I2** | 未實現盈虧**一律**以標記價格計算，任何路徑都不得以最新成交價替代 | R1 |
| **I3** | 一次強平事件**恰好**產生一筆已實現盈虧與一筆手續費，重送觸發不得產生第二筆 | R2 |
| **I4** | 逐倉模式下，單一倉位造成的錢包餘額減損 ≤ 該倉位配置的保證金 | R4 |
| **I5** | reduce-only 訂單執行後，倉位絕對值**必不增加** | R9 |
| **I6** | 任一時刻：`已凍結保證金 = Σ(未成交委託應凍結) + Σ(持倉 IM)` | R5, R10 |
| **I7** | MM 恆以**當前**名目價值查表所得的 MMR 計算 | R7 |
| **I8** | 一個資金費率結算週期內，同一倉位**恰好**被收付一次 | R6 |
| **I9** | 強平完成後：`帳戶淨值 ≥ 0`，若原本為負，差額由保險基金補足並留下紀錄 | R8 |
| **I10** | 帳本結構的保留筆數不隨累計交易量線性成長 | R12 |

> **I1 是總帳不變式。** 它涵蓋範圍最廣、最難違反卻最致命——所有其他不變式都可以看成
> I1 在特定路徑上的特例。任何長時間、隨機操作的測試（§7.3）都應該以 I1 作為最終斷言。

## 5. 測試分層策略

| 層 | 驗什麼 | 為什麼放這一層 | 執行時機 |
|---|---|---|---|
| **單元** | 保證金公式、MMR 分層查表、強平價推導、資金費率計算 | 純函數，可窮舉邊界值，毫秒級 | 每次 commit |
| **元件／API** | 下單校驗與拒絕碼、倉位查詢、參數調整 | 需要服務但不需要撮合 | 每次 PR |
| **整合** | 完整生命週期，含可控標記價與可控時鐘 | 跨元件時序才會暴露的缺陷 | 每次 PR |
| **併發** | R2/R5/R9/R10 的競態 | 只在多執行緒下出現 | 每次 PR |
| **耐久** | I10，長時間運行的資源保留 | **功能測試沒有時間軸** | 每日 |
| **效能** | 連鎖強平的吞吐與延遲 | 極端行情的系統性風險 | 每次發版 |

> **「功能測試沒有時間軸」不是修辭。** 本 repo 的 2026-07 事故中，
> 84 個功能測試全程綠燈，而服務累積了 1,136 萬個無法回收的物件、
> 陷入 114,876 次無效 Full GC。詳見 [`docs/incident-2026-07-14-gc-death-spiral/`](../incident-2026-07-14-gc-death-spiral/)。
> 耐久層存在的理由就是這個。

## 6. 測試案例設計

以下不是完整案例清單，而是**每個區塊中風險最高、最容易被漏掉的那些**。
完整清單在案例管理系統中維護；這裡記錄的是**為什麼要測這些**。

### 6.1 開倉

#### 6.1.1 保證金充足性邊界（R3）

設槓桿 10x、標記價 50,000、數量 0.1 → 名目 5,000 → IM 500。
假設手續費率 0.04% → 開倉手續費 2。所需 = 502。

| # | 可用餘額 | 預期 | 驗什麼 |
|---|---|---|---|
| 1 | 502.00000000 | **接受** | 剛好足夠必須通過——過度保守的拒絕也是缺陷 |
| 2 | 501.99999999 | 拒絕 | 少一個最小單位必須拒絕 |
| 3 | 502.00000001 | 接受 | |
| 4 | 0 | 拒絕 | |

> **為什麼要測「剛好足夠」而不只測「不足」**：只測不足的話，
> 一個把條件寫成 `balance > required` 的實作會通過所有測試，
> 卻讓每一個剛好備足保證金的使用者被拒絕。**邊界要從兩側夾。**

#### 6.1.2 精度與截斷

沿用 `payment-api` 已驗證的原則：**超出精度必須明確拒絕，不得靜默截斷**。

| # | 輸入 | 預期 |
|---|---|---|
| 5 | 數量 0.123456789（超過合約精度） | 拒絕，明確錯誤碼 |
| 6 | 數量 0.10000000（尾隨零） | 接受，不得過度拒絕 |
| 7 | 數量為負 / 零 | 拒絕 |

#### 6.1.3 風險限額分層（R7）

【假設】名目 0–50,000 → 最高 125x；50,000–250,000 → 最高 100x，MMR 更高。

| # | 情境 | 預期 |
|---|---|---|
| 8 | 名目剛好 50,000，用 125x | 接受（邊界屬於低層） |
| 9 | 名目 50,000.00000001，用 125x | 拒絕，或依規則自動降槓桿——**行為必須明確定義** |
| 10 | 已有 40,000 倉位，再開 20,000 跨層 | **合併後**的名目查層，非單筆 |

> 第 10 項是最容易錯的：分層必須依**倉位合併後**的名目，
> 而不是依單筆委託。錯了會低估 MM，強平價算得太寬。

#### 6.1.4 部分成交（R5）

| # | 情境 | 預期 |
|---|---|---|
| 11 | 委託 1.0，成交 0.3 | 持倉 IM 對應 0.3；剩餘 0.7 的凍結保證金仍保留。斷言 **I6** |
| 12 | 成交 0.3 後撤單 | 釋放 0.7 對應的凍結，**不多不少**。斷言 **I6** |
| 13 | 成交 0.3 後剩餘被系統取消（如 IOC） | 同上 |

#### 6.1.5 reduce-only（R9）

| # | 情境 | 預期 |
|---|---|---|
| 14 | 無倉位時下 reduce-only | 拒絕或不成交 |
| 15 | 多倉 1.0，reduce-only 賣 1.5 | 最多只減到 0，不得反向開倉。斷言 **I5** |

### 6.2 持倉

#### 6.2.1 標記價 vs 最新成交價（R1）— **最高優先**

| # | 情境 | 預期 | 驗什麼 |
|---|---|---|---|
| 16 | 注入一筆遠離指數的成交，使**最新成交價**觸及強平價，但**標記價不動** | **不得強平** | 直接驗 **I2**。這是本計畫最重要的單一案例 |
| 17 | 標記價觸及強平價，但最新成交價未觸及 | **必須強平** | 反向驗證，防止「兩個都要滿足才強平」的錯誤實作 |
| 18 | 未實現盈虧顯示值 | 以標記價計算 | 案例 16、17 的前置條件 |

> **案例 16 與 17 必須成對存在。** 只有 16 的話，一個「永不強平」的壞實作會通過；
> 只有 17 的話，用最新成交價的實作也會通過。**成對的案例才能把實作夾在中間。**

#### 6.2.2 資金費率（R6, I8）

| # | 情境 | 預期 |
|---|---|---|
| 19 | 倉位於結算時間戳**前 1ms** 建立 | 收付本期 |
| 20 | 倉位於結算時間戳**後 1ms** 建立 | 不收付本期 |
| 21 | 倉位於結算時間戳**前 1ms** 平倉 | 不收付本期 |
| 22 | 結算作業重跑（模擬重試） | **恰好收付一次**。斷言 **I8** |
| 23 | 結算過程中服務重啟 | 恢復後不重複、不遺漏 |

> 案例 22、23 是把 `payment-api` 的冪等測試手法平移過來。
> 差別只在觸發者從「客戶端重試」變成「排程重試」，
> **但「一個可能重送的觸發會動到錢」這個本質完全相同。**

#### 6.2.3 調整槓桿／保證金（R10）

| # | 情境 | 預期 |
|---|---|---|
| 24 | 持倉中調高槓桿 | IM 釋放、強平價變近；斷言 **I6, I7** |
| 25 | 調整後 MM > 保證金餘額 | 拒絕調整（不得因調整而立即自陷強平） |
| 26 | 逐倉追加保證金 | 強平價變遠；追加額不得超過可用餘額 |

### 6.3 強平

#### 6.3.1 觸發邊界（R3）— 對稱夾擊

| # | 保證金餘額相對 MM | 預期 |
|---|---|---|
| 27 | MM + 1 最小單位 | **不強平** |
| 28 | 恰好 = MM | 依 §2.1 定義（`≤` 觸發）→ **強平**。**規格須明文，不得靠實作決定** |
| 29 | MM − 1 最小單位 | **強平** |

> 案例 28 是規格問題不是實作問題。**如果規格沒寫清楚 `≤` 還是 `<`，
> 我會在測試設計階段就把它當缺陷提出來**——這正是測試左移的價值：
> 在寫程式之前就消除歧義，比事後爭論便宜得多。

#### 6.3.2 冪等（R2, I3）— **與支付同構**

| # | 情境 | 預期 |
|---|---|---|
| 30 | 同一倉位的強平觸發送兩次 | 恰好一次平倉、一次手續費。斷言 **I3** |
| 31 | 兩個執行緒同時觸發同一倉位強平 | 同上；一方必須失敗且**不留下部分效果** |
| 32 | 強平執行中服務崩潰後重啟 | 不得重複執行；狀態可恢復 |

> **這組案例我有直接可類比的實作經驗。** 在 `payment-api` 中，
> 16 條執行緒帶同一 `idempotency_key` 併發呼叫 `createPayment`，
> 靠 `UNIQUE` 約束當最後防線：競爭失敗者 rollback，
> **連自己剛扣的款一起撤掉**，所以帳戶恰好扣一次。
> 強平需要的是同一個性質——只是「一次」的對象從扣款變成平倉。

#### 6.3.3 部分強平與逐倉隔離（R4, I4）

| # | 情境 | 預期 |
|---|---|---|
| 33 | 大倉位觸及強平，減倉後保證金率回到安全 | 只部分減倉，不全平 |
| 34 | 逐倉倉位 A 被強平，帳戶另有倉位 B | B 不受影響；錢包減損 ≤ A 的配置保證金。斷言 **I4** |
| 35 | 全倉模式下同一情境 | 依全倉語意，可動用整體保證金餘額——**與逐倉的差異必須被明確驗證** |

#### 6.3.4 穿倉與保險基金（R8, I9）

| # | 情境 | 預期 |
|---|---|---|
| 36 | 標記價跳空穿過破產價 | 使用者淨值不為負；差額由保險基金吸收並留紀錄。斷言 **I9** |
| 37 | 保險基金不足 | 觸發 ADL，且 ADL 對手方選擇符合排序規則 |
| 38 | 案例 36、37 之後 | 斷言 **I1**（全系統價值守恆） |

## 7. 併發與競態

### 7.1 需要專門設計的競態組合

| # | 併發雙方 | 為什麼危險 |
|---|---|---|
| C1 | 成交回報 ⟷ 撤單 | 撤單釋放的凍結量可能與已成交部分重疊（雙重釋放） |
| C2 | 強平觸發 ⟷ 使用者主動平倉 | 兩者都會平倉；必須恰好一次 |
| C3 | 強平觸發 ⟷ 追加保證金 | 追加若先生效則不應強平；順序必須明確 |
| C4 | 資金費率結算 ⟷ 平倉 | 決定該不該收這一期 |
| C5 | 調整槓桿 ⟷ 成交回報 | IM 以哪個槓桿計算 |

### 7.2 手法

沿用 `ConcurrentIdempotencyTest` 的模式：N 執行緒、`CountDownLatch` 對齊起跑點、
`ExecutorService` 併發送出，事後斷言不變式而非斷言時序。

> **關鍵原則：斷言不變式，不斷言順序。** 併發測試若斷言「A 必須在 B 之前」，
> 它就會變成不穩定測試。斷言「無論誰先，I1 與 I3 都成立」才是可靠的。

### 7.3 隨機化長時測試（混沌）

隨機序列的開倉／加倉／減倉／調槓桿／價格擾動／資金費率結算，跑數萬次操作，
**全程只斷言 §4 的不變式**。這是最有機會抓到未預期時序組合的手法。

種子必須可重現——失敗時要能用同一顆種子重放。

## 8. 耐久與效能

### 8.1 耐久（I10, R12）

**問題**：訂單簿、成交紀錄、倉位歷史、去重集合這類長生命週期結構，
是否隨累計交易量無界成長？

**手法**：與本 repo 既有耐久測試相同——
**輸入量成長 10 倍時，保留筆數與強制回收後的常駐記憶體是否也成長 10 倍？**

參考實作：
- Java：[`OrderBookRetentionTest`](../../trading-engine-simulator/src/test/java/com/binance/trading/endurance/OrderBookRetentionTest.java)
- 前端：[`session-retention.spec.ts`](../../trading-engine-ui/tests/endurance/session-retention.spec.ts)

**防線**：[`tools/check-bounded-collections.sh`](../../tools/check-bounded-collections.sh)（Java）與
[`check-bounded-collections-ts.sh`](../../tools/check-bounded-collections-ts.sh)（TypeScript）
在 CI 中要求每個長生命週期集合，不是有淘汰機制，就是明文聲明 `BOUNDED-BY` 理由。

### 8.2 效能（R11）

**最該測的不是常態吞吐，是連鎖強平。** 極端行情下大量倉位同時觸及強平，
強平引擎的處理速率若跟不上價格移動，損失會擴大。

| 指標 | 為什麼 |
|---|---|
| 強平判定到送出平倉單的延遲 p50 / p99 | p99 才是風險所在 |
| 每秒可處理的強平筆數 | 對照極端行情的預估需求 |
| 積壓深度隨時間變化 | 積壓若單調成長 → 系統會被拖垮 |

> **量測前先量雜訊。** 門檻必須落在量測本身的變異之外，
> 否則這個閘測到的是排程器而不是程式碼。
> 本 repo 前端耐久測試就遇過這件事：同情境兩次跑出 1.64x 與 2.12x 的離散度，
> 大於要偵測的效應，因此該指標最終只記錄不斷言，閘改設在變異僅約 7% 的常駐記憶體上。

## 9. 可測性需求（對系統設計的回饋）

**以下能力若不存在，§6 有相當比例的案例無法自動化。**
這些應在設計階段提出，而不是等測試階段才發現測不了。

| # | 需求 | 沒有它就測不了 |
|---|---|---|
| T1 | 測試環境可**注入標記價格**，且與最新成交價獨立 | 案例 16、17（最高優先風險） |
| T2 | 可控時鐘，能觸發資金費率結算 | 案例 19–23 |
| T3 | 可注入成交回報（含部分成交），不必經過真實撮合 | 案例 11–13 |
| T4 | 強平觸發可由外部重送，用以驗證冪等 | 案例 30–32 |
| T5 | 可查詢**凍結保證金明細**，而非只有彙總值 | 不變式 I6 |
| T6 | 保險基金餘額與變動紀錄可查 | 不變式 I1、I9 |
| T7 | 每筆已實現盈虧帶有可追溯的觸發來源 ID | 不變式 I3 |

> T1 與 T4 特別重要：它們對應風險矩陣中分數最高的兩項。
> **如果系統設計成無法注入標記價、無法重送強平觸發，
> 那麼 R1 與 R2 就只能靠人工推演與程式碼審查覆蓋——
> 這是一個應該在設計評審時就提出的取捨，不是測試階段的既成事實。**

## 10. 進出場準則

### 10.1 進入測試的條件

- 規格已明文定義 §2.1 所有公式與 §6.3.1 的比較子（`≤` vs `<`）
- §9 的 T1–T4 可測性能力已就緒
- 測試環境具備獨立的標記價來源與可控時鐘

### 10.2 通過準則

| 條件 | 門檻 |
|---|---|
| §4 全部不變式 | 100% 有對應自動化斷言且通過 |
| 風險分數 ≥ 6 的項目 | 100% 有對應案例且通過 |
| 併發案例 C1–C5 | 連續 50 次執行無失敗 |
| 混沌測試 | 至少一輪 10 萬次操作，I1 全程成立 |
| 未關閉缺陷 | Blocker / Critical 為 0 |

> **「連續 50 次無失敗」是刻意的。** 併發缺陷跑一次過不代表什麼；
> 一個穩定度只有 98% 的競態，跑一次有 98% 機率騙過你。

## 11. 缺陷分級

| 等級 | 定義 | 例 |
|---|---|---|
| **Blocker** | 違反 §4 任一不變式，或造成資金損失／憑空產生 | 強平重複執行；穿倉未被吸收 |
| **Critical** | 使用者資金正確但狀態錯誤，或風控失效 | 強平價算錯；分層未重新套用 |
| **Major** | 功能不符規格但無資金影響 | 錯誤碼不準確 |
| **Minor** | 體驗或文案 | 訊息用詞 |

## 12. 已知限制

1. **本計畫基於公開慣例，非內部規格。** §2 所有 `【假設】` 必須逐條核對；
   核對結果會直接改變 §6 的邊界值。
2. **撮合引擎以樁模擬。** 撮合本身的正確性不在本計畫涵蓋範圍。
3. **ADL 的對手方排序規則未展開。** 案例 37 只驗證「有觸發且符合排序」，
   排序規則本身需要獨立計畫。
4. **未涵蓋跨交易對的組合保證金。** 見 §1.2。
5. **效能數字的環境依賴性。** §8.2 的門檻只在固定環境下有意義，
   跨環境比較無效——這一點在本 repo 的前端耐久測試中已有實證。
